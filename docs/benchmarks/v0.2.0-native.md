# Batch and Stats measurements on macOS arm64

On the same 16-key workload, durable BatchPut took 15.3 ms per group versus
265 ms for 16 individual Puts. BatchGet also benefited from grouping 32 warm
keys, although it allocated more bytes than building the same ordered result
with individual Gets. An idle Stats snapshot took about 11 ns with either
one or 4,096 live keys. The tables give medians of five rounds.

## Workload and reproduction

Library revision `c1faf3025836b92647fb472218e18d56d8175dfe` (v0.2.0).
Measured 2026-11-19 on an AC-powered Apple M3 Max, 16 CPU cores, 64 GiB RAM,
macOS 26.7.2 (25G332), Darwin 25.6.0, local APFS, Go 1.27.3 and
GOMAXPROCS=4. The temporary DBs used the local APFS Data volume. Go GC,
the automatic cleaner and normal durable acknowledgments were enabled. The
runs used one development host, with no simultaneous benchmark processes.

From the repository root run:

```sh
benchmark/scripts/api-benchmarks.sh
```

The script builds one test binary and runs 35 scenarios in five rounds,
alternating the order of comparative arms. Each timed read produces an
ordered, caller-owned result. Read values are 64 bytes and present keys
are 16 bytes. Distinct values and Stats deltas validate ordering, hits,
misses and missing slots. In the miss arms an untimed read warms the OS file
cache, and a one-entry application cache keeps the measured keys cold.
For typed reads both codecs are StringCodec. The immutable read fixture
keeps group contents equivalent across arms. With concurrent writes only
BatchGet guarantees one point-in-time view.

The small read/write fixtures use 8 KiB maximum records, a 64 KiB segment
target and eight read handles. The 1 KiB writes compare identical groups on
independent synced copies of a closed seed. Each timed write group starts
with a cold application cache sized for the live keys and fits the existing
segment. Setup, open, close and verification after reopen are outside the
timer. Counts verify one versus sixteen commits in the sixteen-key case.
The boundary benchmark separately exercises rotation with default Options.

## Reads

| 64-byte value workload | Raw BatchGet ns/slot | Raw Get loop ns/slot | Typed BatchGet ns/slot | Typed Get loop ns/slot |
| --- | ---: | ---: | ---: | ---: |
| One hot key | 67.65 | 46.61 | 102.6 | 69.01 |
| 32 distinct hot keys | 28.77 | 37.12 | 54.01 | 59.75 |
| 32 distinct application misses, OS warm | 488.2 | 528.9 | 511.9 | 546.6 |
| 32 mixed duplicate/missing slots, OS warm | 264.8 | 417.3 | 291.8 | 431.3 |

The last group has 16 distinct live keys, 24 found positions and eight missing
positions. BatchGet checks a cold record once per distinct live key. The Get
loop must fetch repeated keys again after eviction. For 32 hot keys the raw
batch used 4,608 B/group in 34 allocations, versus 3,200 B in 33 allocations
for the loop. The typed string batch used 8,960 B/group versus 5,504 B.

## Diagnostic comparisons

### Parallel hot Get across releases

The existing 64-byte Get benchmark is identical at v0.1.0 and v0.2.0. We
built it from each tag with the same toolchain, warmed 128 keys, and timed
2,000,000 Gets per arm with no Stats collector. We alternated which binary
ran first across five paired rounds. Parallel ns/op divides elapsed wall
time by total completions across the four workers.

| Hot Get | v0.1.0 ns/op, median (range) | v0.2.0 ns/op, median (range) |
| --- | ---: | ---: |
| One worker | 48.53 (42.71–49.84) | 47.73 (39.02–50.69) |
| Four workers | 195.8 (185.6–231.1) | 295.3 (286.8–319.4) |

The four-worker case took 51% more time per completion at v0.2.0, with
the same direction in every pair. Each version allocated 64 B/op in one
allocation. To reproduce, run this command in a clean checkout of each tag:

```sh
GOMAXPROCS=4 go test ./benchmark -run '^$' -bench '^BenchmarkGet$/^64$/^application-hit(-parallel)?$' -benchtime=2000000x -benchmem
```

In five further pairs against stock v0.2.0, moving only the `stats Stats`
field from immediately after `state` to the end of `internal/engine.DB` in
a temporary build reduced the four-worker median from 309.2 to 195.3 ns/op.
Every pair improved. This isolates sensitivity to field placement on this
host. Establishing a cache-line or locking mechanism requires further profiling.

### BatchGet scratch allocation

The raw 32-key hot path allocates a location slice even when every value is
cached. In an unshipped overlay, batches of up to 32 used a local array of 32
storage locations, with the original heap allocation for larger batches.
The overlay passed the focused BatchGet tests. In five alternating comparisons
of the raw BatchGet arms (250 ms each), median bytes fell from 4,608 to
3,200 and time fell from 898 to 840 ns/group for 32 hot keys. For one hot
key, bytes fell from 144 to 96, but time **rose** from 67.69 to 74.11 ns.
This trade-off matters when choosing a scratch strategy.

### Large BatchPut allocation

A separate allocation profile of the exact-fit BatchPut with an empty active
segment attributed about 32 MiB each to the batch encoder and value cloning
in ownMutation across eight groups (one calibration and seven measured).
The unprofiled median was 8,392,898 allocated bytes per group, approximately
twice the encoded batch size. Allocated-byte totals do not measure peak RSS.
Reproduce the stack attribution with:

```sh
GOMAXPROCS=4 go test ./benchmark -run '^$' -bench '^BenchmarkBatchPutSegmentBoundary$/^empty$' \
  -benchtime=7x -o /tmp/tarp-batch-put.test -memprofile=/tmp/tarp-batch-put.pprof -memprofilerate=1
go tool pprof -top -alloc_space -focus 'mutateBatch' /tmp/tarp-batch-put.pprof
```
