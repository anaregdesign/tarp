# Integrating physical key locality

[Issue #150](https://github.com/anaregdesign/tarp/issues/150) explores keeping frequently scanned ranges together while foreground writes continue to append. The implementation references below are pinned to [main at 59ddf19](https://github.com/anaregdesign/tarp/tree/59ddf199558d73b744c3a1204a10612b3cea446a). The following layouts are proposals. The experiment does not qualify a change to recovery or durability.

## What the current format permits

A full checkpoint at cutoff `C` contains at most one live Put per key, with its original sequence at or below `C`. Snapshot records may appear in any physical order. Raw logs cover consecutive sequences after `C`. Each cleaned log covers a contiguous original interval and stores its survivors in increasing sequence order. Incremental cleaning retains every post-checkpoint Delete and advances the pruned-through frontier so replay can accept a Delete whose earlier Put was pruned. A full checkpoint may drop tombstones through `C` because it replaces the entire older history. [Catalog invariants](https://github.com/anaregdesign/tarp/blob/59ddf199558d73b744c3a1204a10612b3cea446a/docs/format.md#L183-L209)

**A key-ordered full snapshot fits the current format.** Today `Compact` validates history and streams live records in source file/offset order. An optional writer could first validate the same captured history, emit verified live key/address pairs in encoded-key order using a bounded external sort, then copy those records from pinned DATA into target-sized snapshot files. Preserve checksums, original sequences, count/address verification, and the existing repair and loss-handling path. Sorting addresses limits scratch payload but can turn the second pass into scattered source reads. Both index modes can use the same sort. At publication, keep every concurrent tail interval after `C` and invalidate a checkpoint INDEX tied to the replaced layout. An already checkpointed DB currently takes the cleanup-only path at the same sequence, so an explicit request to recluster an existing checkpoint needs a deliberate rebuild path. [Checkpoint copy/install](https://github.com/anaregdesign/tarp/blob/59ddf199558d73b744c3a1204a10612b3cea446a/internal/storage/checkpoint.go#L41-L73) · [Cutoff handling and recovered copy](https://github.com/anaregdesign/tarp/blob/59ddf199558d73b744c3a1204a10612b3cea446a/internal/engine/compact.go#L66-L175) · [Sorted replay reducer](https://github.com/anaregdesign/tarp/blob/59ddf199558d73b744c3a1204a10612b3cea446a/internal/storage/replay_sort.go#L195-L237)

For a fresh import with one final Put per key, the caller can insert pre-sorted batches through the existing API. Each batch has its own commit. Existing databases and streams with repeated Put/Delete operations need a captured logical state before reordering. Subsequent updates append to the active log and dirty only their own versions. Repeatedly updating the smallest key need not move the following keys. Logical file-offset locality can improve coalescing opportunities. Actual sequential I/O also depends on the reader, filesystem allocation and device.

## Recommended physical DATA design for evaluation

Use a **logical full checkpoint at one global cutoff `C`, with file reuse**. Bootstrap by building a verified key-ordered full snapshot. At the next checkpoint, seal and capture the latest complete batch boundary under the writer gate. Validate the captured history and merge every selected delta through `C` with that base. Process the merged live state in encoded-key order for both index modes. All published snapshot files together must contain precisely one Put per live key at its original winning sequence. Omit every key deleted through `C`, including delete/reinsert cases whose final state is absent. This complete coverage permits retiring all captured logs and tombstones through the same `C`. No per-range cutoff or file-format field is needed. [Checkpoint record checks](https://github.com/anaregdesign/tarp/blob/59ddf199558d73b744c3a1204a10612b3cea446a/internal/format/range.go#L57-L92)

- **Reuse whole files with proof.** Establish strict key order within and across the selected base files. For a file with inclusive min/max keys, compare its rows with the complete merged result in that span. Reuse its existing file ID, length, digest and protected bytes only when both streams agree on every key, exact version and validated record. An overwrite with identical value bytes but a newer sequence still dirties the file. An interior insertion forces replacement even if every old row survives. An insertion in a gap between spans, before the first file, or after the last can occupy new files between the unchanged neighbors. Empty results omit the corresponding files. Fence metadata can be derived during validation. Unordered or unproven inputs take the sorted full rebuild path.
- **Write the replacements.** Emit target-sized sorted DATA fragments for dirty spans and populated gaps, assigning new IDs and preparing PARITY for the new files. Reused IDs keep their matching PARITY after integrity checks. Apply existing repair/loss rules to damaged sources before declaring a file reusable. Keep verified ordering when splitting files. The retry/discard list must contain only the newly allocated outputs. Today `Checkpoint` pairs every output entry with a private file and validates copy completeness using relocations. A sharing implementation needs separate selected and newly allocated file lists, plus a completeness check counting both reused and moved records. [Current checkpoint lifecycle](https://github.com/anaregdesign/tarp/blob/59ddf199558d73b744c3a1204a10612b3cea446a/internal/storage/checkpoint.go#L41-L73) · [Output protection and install](https://github.com/anaregdesign/tarp/blob/59ddf199558d73b744c3a1204a10612b3cea446a/internal/storage/checkpoint.go#L136-L192)
- **Select and retire.** Publish one manifest with `Cutoff = PrunedThrough = C`, the complete list of reused and new snapshot IDs in key order, and the entire concurrent tail after `C`. Invalidate the prior physical INDEX descriptor. Use the existing sync, `CURRENT`, uncertain-publication and pin protocol. Reused files remain selected across the change. Skip old-equals-new relocation, file reference updates and replacement byte accounting for them. Conditionally relocate only moved current addresses. Retire superseded files after release of index references and scan/backup pins. A backup of either generation still includes every selected DATA file. [Install and concurrent tail](https://github.com/anaregdesign/tarp/blob/59ddf199558d73b744c3a1204a10612b3cea446a/internal/storage/checkpoint.go#L158-L187) · [Physical accounting](https://github.com/anaregdesign/tarp/blob/59ddf199558d73b744c3a1204a10612b3cea446a/internal/engine/stats_data.go#L63-L75)

This approach reorganizes authoritative DATA. Disabling it leaves ordinary, readable snapshot files. File reuse can reduce candidate output bytes, yet full validation may still read every captured record. Track dirty-file bytes, cumulative delta and tombstone bytes awaiting a checkpoint, projected staging space, pins and foreground headroom. Coalesce repeated attempts, pace staging and defer a job when budgets are exhausted. While deferred, the append tail grows and locality can deteriorate. Widespread changes may warrant a complete rewrite. The native overwrite-only trial counts displaced base files/bytes and the remaining untouched inventory. These figures are inputs to a reuse policy. The trial does not implement structural sharing or measure its checkpoint latency, copied bytes, insertion handling or crash recovery. [Fixture inventory](https://github.com/anaregdesign/tarp/blob/9041abccfe2283eca5c048bfc48bbb5b81dfd3c1/benchmark/locality_native_linux_test.go#L81-L141)

## Bounded range maintenance

**A disposable packed range cache offers a separate read-side experiment.** Capture a bounded key range with its immutable index view and pinned DATA layout. Write verified live records in key order, with an offset directory, source address and sequence per key, and checksums on cached records. Publish the finished immutable extent in process memory. At query time take one normal snapshot. For each matching live key, use the cache only if its full key and source version match that snapshot. Read misses and changed rows from their captured DATA address, and let the snapshot exclude deletions and include new keys. A changed source address after ordinary cleaning can conservatively miss. A read failure in the cache falls back to authoritative DATA. Keep damaged-source handling and backup verification on their normal paths. [Snapshot read contract](https://github.com/anaregdesign/tarp/blob/59ddf199558d73b744c3a1204a10612b3cea446a/internal/engine/scan.go#L27-L111)

On B+tree, an ordered range can consume adjacent cached records together. On the memory hash index, enumerate the range from the same snapshot and group reads by extent and offset within a byte budget. Account for its full-key search and any sorting. Cap extent count, directory memory, staging bytes, retained reader generations, and per-job bytes. Readers pin their selected extent until release. Publish a new generation only after a complete copy. Cancellation, ENOSPC, eviction or process exit can discard it and continue using DATA. Use process-private scratch with an approved cleanup pattern, including recovery of the create-before-unlink window. Backups continue to capture selected DATA and restore can rebuild the cache. Disabling the feature discards the derived layout. [Workspace rules](https://github.com/anaregdesign/tarp/blob/59ddf199558d73b744c3a1204a10612b3cea446a/internal/storage/workspace.go#L36-L84) · [Backup capture](https://github.com/anaregdesign/tarp/blob/59ddf199558d73b744c3a1204a10612b3cea446a/docs/durability.md#L267-L275)

**An authoritative per-range base needs different recovery semantics.** Runs containing arbitrary survivors from overlapping delta intervals cannot be installed as ordinary cleaned logs. Folding selected keys newer than `C` into a snapshot also exceeds its global cutoff. A format proposal must describe nonoverlapping key ranges, a base cutoff per range, and exact delta sequence coverage through the single committed frontier. Replay must reconstruct every range at that frontier, fold each mutation once, and retain tombstones until all older puts they suppress are excluded from replay. A batch spanning ranges must appear atomically on reopen. Preserve completeness and uniqueness across run splits, merges, reinsertion and empty ranges. Update Full/Indexed reopen, repair/parity, backup verification and restore together. Rollback across incompatible formats requires a verified exporter/importer for the target format and a separate destination. Preserve the required identities and sequence history. Quiesce writes for cutover or catch up the tail before switching directories. [Record acceptance](https://github.com/anaregdesign/tarp/blob/59ddf199558d73b744c3a1204a10612b3cea446a/internal/format/range.go#L57-L93) · [Format selection](https://github.com/anaregdesign/tarp/blob/59ddf199558d73b744c3a1204a10612b3cea446a/docs/format.md#L7-L30)

Any authoritative replacement must pin inputs, stream survivors outside the writer gate, and protect and sync immutable outputs. Under the gate, revalidate source identities, rebase on the latest committed tail, and atomically select the synced manifest via `CURRENT`. An uncertain selector rename or directory sync requires fail-stop and validated reopen with both candidate layouts retained. After selection, relocate only entries whose full old address still matches, in count/byte-bounded batches with spill. Later Put/Delete wins. Respect memory-mode staged-write exclusion and the B+tree writer gate. Retire only after catalog selection, live references and all reader/backup pins allow it. Serialize layout publication with the existing cleaner, budget overlap with backups and foreground growth, and yield between bounded maintenance units. [Publication and retirement](https://github.com/anaregdesign/tarp/blob/59ddf199558d73b744c3a1204a10612b3cea446a/docs/durability.md#L217-L264) · [Conditional relocation](https://github.com/anaregdesign/tarp/blob/59ddf199558d73b744c3a1204a10612b3cea446a/internal/engine/index.go#L123-L202)

## Trigger work on read demand and surviving bytes

Track a capped shortlist of recently scanned, disjoint ranges with stable byte fences. Rank jobs by observed scan frequency, reads/bytes outside the base, and estimated bytes to rewrite. Keep cold ranges and sparse exceptions in the append path. Apply a minimum observed benefit, cooldown and a maintenance byte budget so a single repeatedly updated first key cannot schedule continuous range copies.

For a tracked range with base cutoff `C`, count a live record's encoded bytes when its version sequence exceeds `C`. At successful commit, subtract the previous qualifying live record's bytes and add the final qualifying live record's bytes. Delete contributes zero new live bytes. Coalesce repeated keys in a batch against their pre-batch and final states. Track tombstone/log space separately. The dirty counter therefore counts surviving bytes once per key, including size changes. Foreground work uses the old/new addresses already available during commit and a lookup in the bounded range table. It requires no per-update key history. Start tracking from a known capture or initialize by a background count with commit deltas recorded since capture. Record cache misses from cleaner relocations separately. During a rebuild at a new cutoff, maintain a second counter for the in-flight cutoff and swap it with the published base. Discard both the candidate and its counters on a failed build. The old base and its counters continue to serve. [Batch publication](https://github.com/anaregdesign/tarp/blob/59ddf199558d73b744c3a1204a10612b3cea446a/internal/engine/batch_write.go#L148-L254)

Measure current-address DATA pages touched per prefix, bytes actually read, maintenance bytes per committed user byte, peak scratch and pinned bytes, and foreground commit latency under overlapping maintenance. Include overwrite of the smallest key, repeated hot-range updates, scattered sparse updates and cold ranges. Keep the append-only baseline, sorted initial layout and asynchronously rebuilt ranges as distinct arms. Exercise reopen, concurrent delete/reinsert, pinned backups, pre-publication failure and uncertain publication before making a durability claim for an authoritative layout.
